# Scout Mesh: payment\-backed device reauthentication
Replace reusable enrollment credentials and plaintext client keys with password\-protected device identities and recurring, cryptographically verified authorization\.
## Confirmed scope
* Support **Stripe, LINE Pay, and ETH/USDC on Ethereum**\. Use provider sandboxes and Ethereum Sepolia for integration testing; test payments must never grant production entitlements\.
* Users choose their own password and unlock once per application/session\. Renewal is automatic while unlocked; process restart, reboot, or explicit application lock requires another unlock\.
* Preserve the distinction between **one\-time mesh membership** and **recurring access to paid stack APIs**\. Reauthentication never initiates a charge\. Keep the Windows administration path HTTPS\-only and VPN\-free\.

## Device identity and password vault
* An entry token **authorizes enrollment; it is not converted into a private key**\. Generate independent random WireGuard keys and P\-256 authentication keys locally\. Send only public keys and proof of possession to the hub\.
* Replace the production shared token with random, expiring, single\-use tokens stored as hashes and bound to a server\-owned account/order\. Consume tokens atomically with device registration\. A caller\-supplied device ID must never authorize replacement or recovery\.
* Encrypt private keys and sensitive local profile fields with a versioned **Argon2id \+ AES\-256\-GCM** vault using maintained libraries, unique salts/nonces, bounded KDF parameters, and authenticated account/device/server metadata\. Start with Argon2id 64 MiB, three iterations, one lane; benchmark on the target phone before finalizing performance parameters\.
* Android adds a non\-exportable Android Keystore wrapping key so copying the vault alone does not transfer the identity\. Report hardware\-backed protection accurately rather than assuming every device supports it\. Linux uses a password\-encrypted vault and restricted OS storage; without TPM\-backed sealing, do not claim resistance to cloning the entire machine's secrets\.
* Keep unlocked material and access credentials in memory only\. Explicit lock stops renewal, cancels protected requests, tears down the actual WireGuard tunnel, and releases key material\. Password changes re\-encrypt the vault\. Forgotten passwords cannot recover its contents; account recovery must revoke the old identity and authorize a new enrollment, not bypass encryption\.

## Payment verification
All providers resolve to server\-owned orders and independently revocable grants\. Product, amount, currency/asset, service period, account, and provider identifiers come from trusted configuration/order records—not caller claims or an LLM\. Duplicate processing must not extend access; revoking one payment must not erase an unrelated valid grant\.
### Stripe
Verify `Stripe-Signature` against the exact raw body with timestamp tolerance and secret rotation support\. Persist event IDs before acknowledging receipt; reconcile canonical payment/subscription state to handle retries and unordered events\. Check account and test/live mode, configured products/prices, successful settlement, paid periods, cancellation timing, refunds, and disputes\. Use the official SDK rather than regex parsing payment JSON\.
### LINE Pay
Implement the current v4 merchant API with its documented HMAC\-SHA256 request authentication and fresh nonces\. Treat redirects/callbacks only as prompts to verify a previously linked order\. Retrieve payment details over authenticated HTTPS and require actual capture, matching amount/currency/order, and acceptable refund state; HTTP 200 or user authentication alone is not payment proof\. Renewal verification is read\-only and must not issue pre\-approved charges\.
### Ethereum ETH/USDC
* Bind the paying wallet to the account/order using a nonce\-, origin\-, chain\-, and expiry\-bound Sign\-In with Ethereum message\. Begin with ordinary externally owned wallets; explicitly reject unsupported smart\-contract wallet proofs\.
* Verify transactions through an operator\-configured, synchronized Ethereum node\. A locally validating execution/consensus node is preferred; a hosted HTTPS RPC is an explicit trust dependency, not independent cryptographic proof\.
* Require Ethereum mainnet chain ID 1, a successful receipt, canonical block hash and finalized inclusion, the expected payer/receiving address, and the server\-quoted integer amount within the order's payment window\. For USDC, require the allowlisted Circle contract and matching Transfer log; never accept a token merely named USDC\.
* Deduplicate transaction/log claims across accounts and orders\. Pending, failed, wrong\-chain, wrong\-recipient, counterfeit\-token, and pre\-finality reorganized payments grant nothing\. No wallet seed phrases, custody, automatic debits, or deployed payment contract are needed\.
